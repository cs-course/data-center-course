### v2 仿真模型要点（HTML 内实现）

| 要素 | 模型 |
|---|---|
| 服务时间 | lognormal（μ/σ 按负载），节点内**磁盘串行**（队列等待自然产生） |
| 尾部来源 | GC/固件停顿（指数间隔，暂停 250–900ms）+ 坏块级尖刺（0.2%/1.2% 概率 ×25） |
| 扰动开关 | GC 间隔 6s→1.6s、暂停×2、尖刺概率×6，可演示中途热切换 |

| 对冲 | 阈值=滑动窗口(100) P95 或固定值；先到先赢、慢者 tied 取消（在队则真取消、在服务则作废计数） |
| 观测 | 对数纵轴逐请求散点 + 均值/P99 虚线 + CDF + 百分位卡片 + **P99÷均值英雄数字**；对冲模式增列对冲触发数/额外请求%/作废数，三轮结果可保存对照 |

## 1. 设计意图

### 为什么选 RPi + SeaweedFS 而不是笔记本单机

| 方案 | 尾延迟真实性 | 演示可控性 | 结论 |
|---|---|---|---|
| 笔记本单机 + 故障注入 | 弱（NVMe 太快，尾巴要靠演） | 高 | 备选 |
| **RPi 集群（microSD + 百兆）** | **强（真实设备的天然波动）** | 中高 | **主选** |
| 录屏/数据回放 | — | 最高 | 兜底 |

核心卖点正是讲座原话：「即便是这样一个**小巧**的对象存储服务（1GB 内存、SD 卡、百兆网），尾延迟照样触目惊心」——小问题里藏着真科学，这正是博士生该建立的直觉。

### 两个演示的功能分工

- **演示一（开场，12 分钟）**：破刻板印象。听众预期「小系统性能指标 = 平均延迟 + 峰值带宽」，演示用四种典型负载证明**均值岁月静好、P99 惊涛骇浪**。
- **演示二（收尾，15 分钟）**：立方法论。用一个 ~15 行 Python 的预测对冲算法，现场把 P99 打下去，证明**简单直白的逻辑就能撬动真问题**，并指出开放的优化空间（阈值自适应、负载感知、拥塞时对冲反而有害）——留给听众的研究钩子。

## 2. 拓扑与物料

```
        笔记本（负载端 + 实时绘图，HDMI 投屏）
            │ 千兆/百兆交换机（自带，不依赖教室网络）
   ┌────────┼────────┬──────────┐
 rpi001   rpi002   rpi003    rpi004(扰动节点)
 master+   volume   volume   后台跑 stress-ng / tc netem
 filer     (副本A)  (副本B)   制造"straggler"
```

- **SeaweedFS 部署**：rpi001 跑 master + filer；rpi002/rpi003 各跑 volume，`replication=001`（每对象双副本，两机各一份）。已有 registry（raspberrypi.local:5000）和部署经验，提前一晚配好并烧入数据集。
- **扰动注入**：rpi003 上预备三个档位的干扰脚本（`stress-ng --hdd`、`tc qdisc netem delay`、或定时 `sync` 风暴），演示中远程一键开关，模拟「坏块/GC/邻居拥塞」——讲座里 Source-of-Latency 那张图的现实版。
- **数据集**（对应讲座 MLPerf 负载表，各负载备独立 bucket）：

| 负载 | 对象规格 | 数量 | 模拟场景 |
|---|---|---|---|
| L1 大对象顺序读 | 8 MB | 200 | LLM Checkpoint |
| L2 小对象随机读 | 200 KB | 5000 | ImageNet 训练喂数据 |
| L3 混合读写 70/30 | 1 MB | 2000 | 通用 Web 应用 |
| L4 突发访问（on-off 30s/30s）| 512 KB | 1000 | 竞价实例/批处理窗口 |

- **负载端**：笔记本 Python + boto3（或直接 HTTP），每条请求记录 `{ts, op, size, latency_ms, replica}` 写 CSV。不用 s3bench/WARP 做主测量——它们能出吞吐但逐请求时间戳不如自采灵活；可在准备阶段用 warp 跑一遍基线备查。
- **可视化**：一个静态 HTML 页（沿 demos/ 约定放 `demos/tail-latency-live.html`，走 compile.sh 3.5 步进 public），fetch 本地 CSV 增量刷新，双面板：左时序散点、右 CDF + 百分位数字（mean/P50/P90/P99/P999/max）。若来不及做实时版，降级为每轮跑完用 matplotlib 出图投屏。

## 3. 演示一（开场，12 分钟）：均值在说谎

### 流程

1. **铺垫（2 min）**：亮出拓扑——「这就是全部家当」。口头给出在轻载下实测的平均延迟（如 L2 均值 ~15ms），显得一切正常。
2. **POE-Predict（2 min）**：发便利贴/在线表单，每人写下预测：「L2 负载下 **P99 ÷ 均值** 会是多少倍？」收齐后口头抽样两个答案。（**此环节不可省**，省了整个演示学习增益归零。）
3. **Observe（6 min）**：
   - L1 跑 60s → 出图：均值 vs P99（预期差距 5–10×）；
   - L2 跑 90s，**第 45s 时远程打开 rpi003 扰动** → 时序图上肉眼可见的尖刺带，P99 飙升至均值 30–100×，而均值只挪动一点点；
   - 快切 L3/L4 各 45s，指出「混合写放大」「突发冷启动」各自不同形态的尾巴。
4. **Explain（2 min）**：回扣讲座——均值被平均掉了（"Everything You Know About Latency Is Wrong"），扇出放大（The Tail at Scale：100 台 P99=1s 的服务器并行，63% 请求超 1s）。「刚才 2 台 volume 你们已经看到了，100 台会怎样？」

### 成功判据

- L2 扰动后 P99/均值 ≥ 20×（RPi microSD 天然可达；不够就加大扰动档位）；
- 均值变化 < 2×——**对比感是全部卖点**。

## 4. 演示二（收尾，15 分钟）：15 行代码驯服长尾

### 算法（投屏逐行讲，真的就这么点）

```python
window = deque(maxlen=100)          # 最近100次延迟
def get(obj):
    t = percentile(window, 95) if len(window) >= 20 else INF
    r1 = async_get(replica_A, obj)  # 先发最优副本
    if r1.wait(t):                  # 超过预测阈值
        r2 = async_get(replica_B, obj)   # 补发对冲请求
        res = first(r1, r2); cancel(other)
    else:
        res = r1.result()
    window.append(res.latency)      # 滑动窗口在线更新预测
    return res
```

要点三句话：**阈值不是拍脑袋常数，是滑动窗口实时预测的 P95**（字节跳动动态阈值的极简版）；**先到先用、慢者取消**（hedged + tied 的思想）；**额外开销天然受限**——只在最慢的 ~5% 请求上多花一次读。

### 流程

1. **POE-Predict（2 min）**：同一批听众再写两数：「对冲后 P99 降百分之几？额外流量多百分之几？」
2. **Observe（8 min）**：复跑演示一的 L2（含扰动全程开启），三轮各 90s，同屏对比 CDF：
   - 轮 A：无对冲（基线，复现开场惨状）；
   - 轮 B：固定阈值对冲（阈值=开场实测 P95）；
   - 轮 C：**预测对冲**（滑动窗口动态阈值）。
   - 每轮结束读三个数：P99、P999、额外请求占比。
3. **Explain + 研究钩子（5 min）**：
   - 预期结果：轮 B/C 把 P99 压回接近无扰动水平，额外流量 < 8%；轮 C 在负载切换时恢复更快（阈值自适应 vs 固定阈值失效）——这就是「预测」的价值；
   - 抛三个开放问题收尾：**阈值怎么预测得更准**（时序模型/RL，呼应 ATC'24 RL-Watchdog）；**拥塞时对冲火上浇油怎么办**（何时该"try really hard"，呼应 SNIA fail-fast）；**纠删码下对冲的代价结构完全不同**——每一个都是一篇论文的口子。

### 成功判据

- 轮 C 的 P99 ≤ 基线的 1/3；
- 额外请求占比 ≤ 10%——「两个数都要亮出来，这才是工程」。
